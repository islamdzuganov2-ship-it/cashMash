# 🚀 15 · Развёртывание и эксплуатация

## 15.1 Контуры

| Контур | Назначение | Требования |
|--------|-----------|-----------|
| **DEV** | разработка, мок-биржа, юнит-тесты | любая машина |
| **TESTNET** | полный цикл на `api-testnet.bybit.com` | тот же образ, что PROD, отдельные ключи и данные |
| **PROD** | live, $5 → далее | Linux, 1–2 vCPU / 2 ГБ / SSD, Docker |
| **COLLECTOR** | непрерывный сбор данных ([[23-Data-Pipeline]]) | минимальные требования, но **постоянное место** |
| **RESEARCH** | бэктесты, WFA, CPCV | много ядер. **Никогда не PROD** |

RESEARCH отдельно потому, что оптимизация утилизирует CPU полностью, а живой процесс в этот момент начнёт опаздывать с обработкой WebSocket — и вы спишете это на биржу.

## 15.2 Хостинг меняется — что из этого следует

Заказчик зафиксировал (Q9): площадка запуска непостоянна и может меняться в любой момент. Это не мелочь конфигурации, а требование к архитектуре, и у него есть один неочевидный и неприятный побочный эффект.

### Проблема: привязка ключа к IP

В [[10-Security]] и [[21-Rate-Limits-and-Bans]] зафиксировано требование: **API-ключ Bybit привязывается к IP сервера**. Это главная защита от того, что утёкший ключ сработает откуда угодно. При меняющемся хостинге привязка перестаёт работать: каждый переезд ломает ключ.

Соблазн — снять привязку. Делать этого не следует: ключ без привязки живёт ограниченный срок, а при утечке работает из любой точки мира и позволяет слить счёт намеренно убыточными сделками, даже без права вывода.

### Решение: разделить «где считает» и «откуда ходит»

```
   считать можно где угодно            ходить на биржу — всегда отсюда
┌──────────────────────────┐        ┌─────────────────────────────┐
│ торговый процесс         │        │ ФИКСИРОВАННАЯ ТОЧКА ВЫХОДА  │
│ ноутбук / VPS / другой   │──VPN──▶│ дешёвый VPS, статический IP │──▶ Bybit
│ VPS / что угодно         │        │ WireGuard-сервер            │
└──────────────────────────┘        └─────────────────────────────┘
```

Один постоянный узел с фиксированным IP — это всё, что нужно, чтобы привязка ключа работала. Вычисления при этом переезжают свободно. Стоит такой узел единицы долларов в месяц и решает сразу три задачи:

1. **IP для привязки ключа** остаётся неизменным;
2. **сборщику данных** ([[23-Data-Pipeline]]) нужно ровно такое место — постоянное, дешёвое, без ключей;
3. **предсказуемая латентность** до биржи вместо лотереи.

Если такой узел не появится, альтернатива — ключ без привязки к IP плюс компенсирующие меры: более частая ротация, обязательный субаккаунт с ограниченной суммой, алерт на каждый вход в аккаунт. Это заметно хуже, и решение стоит принять осознанно, а не по умолчанию.

### Требования к переносимости

```
□ Всё состояние — в ОДНОМ каталоге data/. Перенос = копирование каталога.
□ Конфигурация — YAML в git + секреты в ops/.env. Никаких путей,
  зашитых в код, и никаких допущений о структуре хоста.
□ Docker-образ с фиксированным дайджестом базы: одинаковое поведение
  на любом хосте, включая версию Python и системные библиотеки.
□ Всё время — UTC. Часовой пояс хоста не используется нигде.
□ Проверка часов при старте обязательна: на новом хосте NTP может быть
  не настроен, а Bybit отклоняет запросы с расхождением времени.
□ RTT замеряется при старте и пишется в лог. Бот не предполагает
  низкую задержку — он её измеряет.
□ Первый запуск на новом хосте — SIGNAL_ONLY на сутки.
□ Перед переездом: FLATTEN (закрыть позиции) → остановка → перенос →
  реконсиляция на новом месте. Не «просто запустить второй экземпляр».
```

### Адаптация к задержке

Так как RTT меняется от хоста к хосту, он становится входным параметром, а не константой:

| Замеренный RTT p95 | Реакция |
|-------------------|---------|
| < 50 мс | норма, работаем как задумано |
| 50–200 мс | WARN в лог; `post_only_ttl_sec` увеличивается, `cost_gate_k` поднимается |
| 200–500 мс | только `POST_ONLY`, taker-вход запрещён: на такой задержке рыночный вход даёт непредсказуемую цену |
| > 500 мс | `MANAGE_ONLY` + алерт. Торговать с такой задержкой на горизонте в минуты уже нельзя |

Замер — при старте и раз в 5 минут, отдельным лёгким запросом. Это дешевле, чем обнаружить проблему по проскальзыванию через неделю.

> ⚠️ **Чего нельзя делать ни при каких обстоятельствах:** запускать второй экземпляр на новом хосте, не остановив первый. Два процесса на одном аккаунте и символе — это гонки, двойные ордера и взаимно затираемые стопы. Защита: при старте бот проверяет свежесть чужого `heartbeat.json` в общем хранилище и отказывается стартовать, если другой экземпляр жив.

## 15.3 Время — всё в UTC

Крипта работает 24/7, естественной границы суток нет. Конвенция проекта:

- **все** внутренние метки времени — UTC, миллисекунды;
- торговые сутки = сутки UTC (граница дневных лимитов);
- расчёты фандинга — по расписанию биржи в UTC;
- локальное время — только в человекочитаемом выводе, больше нигде;
- NTP-синхронизация обязательна; offset до биржи отслеживается отдельно ([[09-Reliability-and-State]], 9.4).

## 15.4 Сборка и запуск

```
ops/
├── Dockerfile              multi-stage, non-root, фиксированный дайджест базы
├── docker-compose.yml      бот + локальный сборщик метрик
├── cashmash.service        systemd unit
├── watchdog.py             внешний сторож (systemd timer)
├── backup.sh               ежедневный бэкап state.db и конфигов
├── checklist-prod.md       чек-лист запуска
└── CHANGELOG-PROD.md       журнал изменений продакшена
```

```bash
# сборка с фиксацией зависимостей по хэшам
docker build -t cashmash:$(git rev-parse --short HEAD) -f ops/Dockerfile .

# запуск (ключи — из окружения, не из образа)
systemctl --user start cashmash
journalctl --user -u cashmash -f
```

Образ не содержит секретов. Версия образа = хэш коммита. `latest` не используется нигде.

### Подключение счёта

Ключ вводится в робота, а не в конфиг: `python ops/bybit_login.py` (или карточка «Подключение биржи» в панели — она принимает ключ только с петлевого адреса). Робот синхронизирует часы, спрашивает `/v5/user/query-api`, и **отказывает** ключу с правом Withdraw, ключу Read-Only и ключу без прав на торговлю. Предупреждает — об отсутствии привязки к IP, о близком сроке истечения и о MAINNET. Записывает только после того, как биржа ключ подтвердила: `ops/.env`, права 600.

```bash
python ops/bybit_login.py --status    # что подключено
python ops/bybit_login.py --check     # перепроверить на бирже
python ops/bybit_login.py --logout    # забыть ключ
```

Сеть выбирает **конфиг**, а не ключ. Ключ не от той сети биржа отвергает тем же «неверный ключ», что и опечатку, поэтому несовпадение ловится при подключении и при старте процесса (`KEY_NETWORK` → `MANAGE_ONLY`).

В контейнере ключи по-прежнему приходят из окружения: переменная старше файла. Если файл изменили, а процесс уже работает со старой переменной, панель и `run.py --check` об этом говорят отдельной строкой — иначе отчёт показывал бы один ключ там, где работает другой.

## 15.6 Регламент эксплуатации

| Периодичность | Действие |
|--------------|---------|
| Ежедневно | Дайджест: сделки, PnL, ошибки, maker ratio, использование лимитов. Heartbeat свежий? |
| Еженедельно | Отчёт по качеству исполнения (11.6). Факт против модели издержек. Место на диске |
| Ежемесячно | Сверка live-статистики с бэктестом того же периода. Обновление истории. Проверка бэкапа восстановлением. Сверка комиссионного уровня |
| Ежеквартально | Полный ре-WFA на обновлённой истории. Сравнение текущих параметров с новыми оптимальными; замена **только** при систематическом расхождении |
| При инциденте | Runbook 15.6 |

## 15.7 Runbook: типовые инциденты

### И1. Бот не торгует

```
1. heartbeat.json → какой режим? LIVE / MANAGE_ONLY / PAUSED
   MANAGE_ONLY сразу после старта → смотреть лог на NO_KEYS и
   KEY_NETWORK: счёт не подключён или ключ не от той сети.
   Проверить: python ops/bybit_login.py --check
2. Лог: последние записи DECISION → какое veto?
   COST          → эдж не покрывает 7.5 bps; рынок тихий. НОРМА
   FUNDING_WINDOW→ окно фандинга. НОРМА
   SPREAD        → спред вне нормы
   LIMIT_DAY     → дневной лимит исчерпан. НОРМА, не чинить
   BOOK_DESYNC   → стакан рассинхронизирован → см. И4
   CLOCK         → часы разошлись → проверить NTP
   RATE_BUDGET   → упёрлись в лимиты → см. И3
   MIN_NOTIONAL  → расчётный объём ниже минимума биржи
   RECONCILE     → расхождение с биржей → см. И5
3. Veto нет и сигналов нет → проверить прогрев и живость WS
```

### И2. Серия убытков / просадка

```
1. НЕ ВЫКЛЮЧАТЬ И НЕ МЕНЯТЬ ПАРАМЕТРЫ В МОМЕНТЕ.
   Бот уже снизил ставку (risk_factor) и остановится по лимиту.
2. Сравнить текущую серию с максимальной в бэктесте и с p95
   Монте-Карло. В пределах — это ожидаемое поведение.
3. Вне пределов — разобрать по 11.3: исполнение или сигнал?
4. Решение об остановке — по правилу, записанному ЗАРАНЕЕ (17.6).
```

### И3. HTTP 403 / превышение лимитов

```
1. Бот уже остановил исходящие на ban_cooldown_sec и алертнул.
2. Позиция защищена БИРЖЕВЫМ стопом — проверить, что он стоит
   (через веб-интерфейс биржи, не через бота).
3. Разобрать по логам: какой эндпоинт и какой цикл дал всплеск.
   Типичные причины: трейлинг без min_step, опрос вместо WS,
   цикл реконсиляции при падающем боте.
4. Исправить причину. НЕ «увеличить cooldown и жить дальше».
5. Повтор в течение суток → PAUSED до разбора.
```

### И4. Рассинхрон стакана

```
1. Бот уже наложил вето на вход и запросил снапшот.
2. Не восстановилось за 3 попытки → переподключение WS.
3. Повторяется часто → проблема сети или неверная обработка
   последовательности обновлений. Это дефект кода, а не «бывает».
```

### И5. Реконсиляция не сошлась

```
1. Бот в MANAGE_ONLY, новые входы запрещены.
2. Открыть веб-интерфейс Bybit, сверить позиции со списком в логе.
3. Лишняя позиция → чья? Проверить orderLinkId в истории.
   Наш префикс → дефект идемпотентности, СРОЧНО разобрать.
   Не наш → кто-то торгует на том же аккаунте.
4. Недостающая → закрыта вручную или по стопу? Проверить историю.
5. Возврат в LIVE — только после ручного подтверждения.
```

### И6. Сервер перезагрузился

```
1. systemd поднял сервис? journalctl -u cashmash
2. Бот стартовал → реконсиляция → восстановление накопительного состояния
3. Дневной baseline сохранён? Лимиты не сброшены?
4. Позиция: стоп на бирже на месте?
5. Состояние не восстановилось → MANAGE_ONLY, нужно подтверждение
```

## 15.8 Правила изменения продакшена

```
✗ Не менять конфиг «на живую» при открытой позиции
✗ Не пересобирать образ, пока позиция открыта
✗ Не оптимизировать на PROD-машине
✗ Не «подкручивать» риск после серии убытков — этим занимается
  risk_factor по формуле
✗ Не увеличивать лимиты запросов вместо исправления причины всплеска

✓ Изменения — в окно без открытых позиций
✓ Каждое изменение: git-коммит + новый тег образа + запись
  в CHANGELOG-PROD.md с обоснованием
✓ После изменения — минимум сутки на testnet, потом mainnet
✓ Откат: предыдущий образ хранится и проверен на запуск
```
