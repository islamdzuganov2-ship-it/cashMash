# 🧱 02 · Выбор стека

> **Платформа определена:** Bybit, USDT-перпетуалы, собственный аккаунт, REST + WebSocket V5 API. MetaTrader и MQL5 к задаче отношения не имеют — они существуют только внутри терминала форекс-брокера.

## 2.1 Где на самом деле узкое место

Прежде чем выбирать язык, стоит посмотреть на бюджет задержки от сигнала до исполнения:

| Стадия | Типичное время | Кем определяется |
|--------|---------------|------------------|
| Разбор WS-сообщения, обновление состояния | **20–200 мкс** | ваш код |
| Расчёт сигнала и риска | **10–100 мкс** | ваш код |
| Сериализация и подпись запроса | 10–50 мкс | ваш код |
| **Сеть до api.bybit.com** | **10 000–80 000 мкс** | география, провайдер |
| Матчинг на стороне биржи | 1 000–10 000 мкс | биржа |

Локальные вычисления занимают **порядка 0.3%** общего бюджета. Переписывание расчётного слоя с Python на Rust экономит сотни микросекунд там, где доминируют десятки миллисекунд. Это не то место, где живёт эффективность.

**Что реально влияет на задержку, в порядке убывания:**

1. Расположение сервера относительно матчинг-движка Bybit (Сингапур / AWS ap-southeast-1) — экономит **десятки миллисекунд**;
2. Постоянное keep-alive HTTP-соединение вместо нового TLS-хендшейка на каждый ордер — **10–100 мс**;
3. WebSocket Trade API вместо REST для постановки ордера — единицы миллисекунд;
4. Отсутствие лишних сетевых обращений на горячем пути (всё состояние — в памяти) — миллисекунды;
5. И только потом — язык.

## 2.2 Рекомендация

**v1 — Python 3.12 + asyncio. v2 — Rust, но только если профилирование это потребует.**

Это не компромисс «ради простоты». Для данной задачи Python **корректный** выбор, и вот честное сравнение:

| Критерий | Python 3.12 + asyncio | Rust (tokio) | Go |
|----------|----------------------|--------------|-----|
| Скорость разработки | **1x** | 3–5x дольше | 1.5–2x |
| Вклад в общую задержку | пренебрежимый | пренебрежимый | пренебрежимый |
| Предсказуемость задержки (p99) | GC-паузы единицы мс | **детерминированно** | GC-паузы < 1 мс |
| Ошибки в рантайме | **главный минус** | ловятся компилятором | средне |
| Экосистема для research | **лучшая** | слабая | слабая |
| Библиотеки Bybit | `pybit` (официальная) | самописное / `barter-rs` | самописное |
| Порог, где даёт выигрыш | — | HFT, маркет-мейкинг, > 100 ордеров/с | — |

Главный риск Python — не скорость, а то, что ошибка типа обнаруживается в рантайме, в торговом пути, на живых деньгах. Это лечится дисциплиной, и дисциплина обязательна:

```
□ mypy --strict на весь торговый код, в CI, блокирует мёрж
□ pydantic-модели на каждый ответ API: неожиданное поле или тип —
  это ошибка немедленно, а не «None» через три шага
□ Запрет голых except: перехват только конкретных исключений
□ asyncio: только structured concurrency (TaskGroup), никаких
  «осиротевших» create_task, чьё исключение молча съедается
□ Глобальный обработчик: необработанное исключение в любой таске
  = немедленный переход в MANAGE_ONLY + алерт, а не тихая смерть
□ Все деньги и цены — Decimal, НИКОГДА float
□ pytest с покрытием торгового пути > 90%
```

Последний пункт про `Decimal` не педантизм: `0.1 + 0.2 != 0.3` в float, а биржа отклоняет ордер с количеством, не кратным `qtyStep`. Ошибки округления в объёме — стабильный источник отказов.

### Порог перехода на Rust

Переписываем исполнительное ядро, **только если** выполнено хотя бы одно:

- p99 времени от получения WS-события до отправки ордера > **5 мс** локально (замер, не ощущение);
- частота торговых действий превышает ~50 в секунду;
- стратегия становится маркет-мейкингом, где важна позиция в очереди заявок;
- GC-паузы измеримо влияют на исполнение (видно в телеметрии как корреляция пауз и проскальзывания).

До этих порогов Rust даёт худшее отношение результата к затратам: то же исполнение за втрое большее время разработки.

## 2.4 Почему не ccxt в торговом пути

`ccxt` — прекрасная библиотека для того, для чего она сделана: единый интерфейс к сотне бирж. Именно это и мешает:

| Проблема | Последствие |
|----------|------------|
| Абстракция по наименьшему общему знаменателю | Специфика Bybit (`orderLinkId`, режимы позиции, `reduceOnly`, post-only семантика) либо недоступна, либо ведёт себя неочевидно |
| Заголовки лимитов не пробрасываются наружу | Невозможно построить честный лимитер из [[21-Rate-Limits-and-Bans]] |
| Свой внутренний throttle | Конфликтует с вашим приоритетным бюджетом запросов |
| Ошибки приводятся к общим типам | Теряется различие между «повторить» и «не повторять ни в коем случае» |
| Задержка на нормализацию | Мелочь, но бесплатная только на бумаге |

**Решение:** в торговом пути — прямые HTTP/WS вызовы к Bybit V5 (или официальный `pybit` как тонкая обёртка), с собственными pydantic-моделями. В research — `ccxt` сколько угодно.

## 2.6 Обязательные инструменты качества

| Инструмент | Роль | Блокирует мёрж |
|-----------|------|---------------|
| `mypy --strict` | типы в торговом коде | ✅ |
| `ruff` | линт + формат | ✅ |
| `pytest` + покрытие | тесты, включая мок-биржу с инжекцией ошибок | ✅ |
| `pip-audit` | уязвимости зависимостей | ✅ |
| Фиксация версий (`uv.lock` / `poetry.lock`) | воспроизводимость | ✅ |

**Мок-биржа — обязательный компонент, а не «хорошо бы».** Это локальный сервер, повторяющий формат ответов Bybit и умеющий по команде отдавать любую ошибку: 10006, 403, таймаут, разрыв WS, частичное исполнение, расхождение часов. Без него ветки обработки ошибок не тестируются никогда — а именно они решают, потеряете вы деньги или нет.
