# 🔐 10 · Безопасность

## 10.0 Что понимается под «защитой от блокировки»

За формулировкой стоят три разные задачи, и разводить их надо сразу:

| Толкование | Статус | Где решается |
|-----------|--------|-------------|
| **Бот блокирует сам себя**: лимиты запросов, бан по IP, рассинхрон часов | ✅ основная задача | [[21-Rate-Limits-and-Bans]] |
| **Устойчивость к сбоям**: обрывы, падения, перезапуски | ✅ | [[09-Reliability-and-State]] |
| **Защита аккаунта и средств**: ключи, сервер, доступ | ✅ этот документ |
| **Защита кода от копирования** | ✅ 10.5, с честной оценкой пределов |
| **Обход geo-ограничений, KYC, санкционных проверок** | ❌ вне проекта | — |

Последнее не техническая задача, а нарушение условий биржи, которое заканчивается заморозкой средств — причём средства замораживаются вместе с открытыми позициями, и сделать с ними нельзя ничего. Если доступ к Bybit ограничен в вашей юрисдикции, это вопрос выбора площадки, а не архитектуры бота.

## 10.1 Модель угроз

| # | Угроза | Вероятность | Ущерб | Митигация |
|---|--------|------------|-------|-----------|
| T1 | Утечка API-ключа (git, лог, скриншот, чат) | **высокая** | полный слив счёта | 10.2 |
| T2 | Компрометация сервера | средняя | полный | 10.3 |
| T3 | Фишинг / кража доступа к аккаунту биржи | средняя | полный, включая вывод | 10.4 |
| T4 | Вредоносная зависимость (typosquatting в PyPI) | **средняя** | полный — код читает ваши ключи | 10.6 |
| T5 | Ошибка оператора: боевые ключи в тестовом окружении | **высокая** | высокий | 10.7 |
| T6 | Самоблокировка по лимитам | **высокая** | средний | [[21-Rate-Limits-and-Bans]] |
| T7 | Утечка логов с историей сделок | низкая | средний | 10.8 |
| T8 | Кража кода стратегии | низкая | средний | 10.5 |

Порядок не случаен: **утечка ключа и вредоносная зависимость опаснее всего**, потому что дают полный доступ мгновенно и без взлома сервера.

## 10.2 API-ключи — главный периметр

```
□ Права: ТОЛЬКО торговля (Unified Trading / Contract).
  «Withdraw» — НИКОГДА, ни при каких обещаниях удобства.
□ Привязка к IP сервера обязательна. Без неё утёкший ключ работает
  из любой точки мира; с ней — только с вашего адреса.
□ Три разных ключа: боевой (trade), мониторинг (read-only), testnet.
  Разные ключи — разный радиус поражения.
□ Хранение: переменные окружения контейнера или файл с правами 600,
  владелец — непривилегированный пользователь сервиса.
  НИКОГДА: в коде, в git, в YAML-конфиге, в Docker-образе, в логах.
□ .gitignore на .env — в ПЕРВОМ коммите, до того как туда попал секрет.
□ Git-хук или pre-commit с детектором секретов (gitleaks / detect-secrets).
□ Маскирование в логах: пишется только префикс ключа (первые 4 символа).
  Подпись запроса не логируется никогда.
□ Ротация: при любом подозрении, при смене исполнителя, планово раз в
  квартал. Ротация должна быть отработана заранее, а не изобретаться
  в момент инцидента.
□ Отдельный субаккаунт Bybit под бота: ограничивает ущерб суммой
  на субаккаунте, а не всем портфелем.
```

> Ключ без права вывода — не «безопасный ключ». Злоумышленник сливает счёт намеренно убыточными сделками против своей же позиции. Это медленнее прямого вывода, но результат тот же. Поэтому IP-привязка обязательна, а не желательна.

**Если ключ утёк** — порядок действий, записанный заранее:

```
1. Удалить ключ в кабинете Bybit (это мгновенно, делать первым)
2. Закрыть позиции вручную, если бот недоступен
3. Сменить пароль и проверить настройки вывода и белый список адресов
4. Проверить историю API-доступа и сделок
5. Выпустить новый ключ, с IP-привязкой
6. Разобрать, как утёк, и закрыть канал утечки
```

## 10.3 Сервер

```
□ Linux, минимальный образ, только нужные пакеты.
□ SSH по ключу; парольная аутентификация отключена; root-логин запрещён.
□ Порт SSH нестандартный + fail2ban; ещё лучше — доступ только
  через VPN (WireGuard).
□ Файрвол: входящие deny by default (кроме SSH/VPN);
  исходящие — allow-list: api.bybit.com, stream.bybit.com, NTP, канал алертов.
□ Бот работает от непривилегированного пользователя, в контейнере,
  без --privileged, с read-only файловой системой кроме каталога данных.
□ Автообновления безопасности включены; перезагрузки — контролируемо.
□ На торговом сервере нет ничего лишнего: ни браузера, ни чужих скриптов,
  ни «полезных утилит» с форумов.
□ Аудит входов: алерт при любом успешном SSH-подключении.
□ Бэкап: state.db, конфиги, логи — ежедневно, на отдельное хранилище.
□ Отдельная машина для research: бэктесты грузят CPU и мешают live.
```

## 10.4 Аккаунт биржи

```
□ 2FA (TOTP, не SMS) на вход, вывод и изменение настроек API.
□ Антифишинговый код Bybit включён — помогает отличить письма биржи.
□ Белый список адресов вывода + задержка на добавление нового адреса.
□ Отдельная почта под биржу, с 2FA, не используемая нигде больше.
□ Никогда не вводить seed-фразы и пароли по ссылкам из писем и чатов.
□ Регулярная проверка активных API-ключей и сессий: лишние — удалять.
```

## 10.5 Защита кода — честная картина

| Мера | Реальная стойкость |
|------|-------------------|
| Приватный репозиторий | Зависит от дисциплины доступа. Основная мера для «бота для себя» |
| Обфускация Python | **Практически нулевая.** Байткод декомпилируется, `pyarmor` и аналоги обходятся |
| Компиляция в бинарник (nuitka/pyinstaller) | Низкая. Поднимает планку, не более |
| Переписывание на Rust | Средняя. Реверс бинарника дороже, но возможен |
| **Вынос генерации сигнала на свой сервер**, клиент получает только команды | **Высокая.** Алгоритм физически не у клиента |

**Вывод:** если бот только для вас — достаточно приватного репозитория и дисциплины с секретами. Если бот пойдёт к третьим лицам, единственная реальная защита — серверная архитектура, а не обфускация.

Что обязательно в любом случае: лицензионная или иная проверка работает **fail-closed** (не смогли проверить → не торгуем), и никакого деструктивного поведения при провале проверки. Бот, закрывающий позиции в убыток из-за проблемы с лицензией, — это дефект, а не защита.

## 10.6 Цепочка поставки зависимостей

Питон-пакет, установленный в окружение бота, читает ваши переменные окружения. То есть **любая вредоносная зависимость = утечка ключей**.

```
□ Зависимости зафиксированы lock-файлом с хэшами.
□ pip install --require-hashes в продакшн-сборке.
□ Никаких установок «на живую» на боевом сервере — только пересборка
  образа из зафиксированного манифеста.
□ pip-audit в CI, блокирует мёрж при известных уязвимостях.
□ Минимум зависимостей. Каждая новая — осознанное решение
  с проверкой популярности, активности и сопровождения.
□ Проверка имён пакетов на опечатки (typosquatting): «requsts»,
  «pybit-official», «python-bybit» и подобное.
□ Docker-образ собирается из официального базового, с фиксированным
  дайджестом, а не тегом latest.
□ Сканирование образа (trivy) в CI.
```

## 10.7 Защита от ошибки оператора

Самая частая причина потерь — не хакер, а человек в три часа ночи.

```
□ Testnet и mainnet — РАЗНЫЕ конфиги, разные ключи, разные каталоги
  данных. Бот при старте печатает крупно: TESTNET или MAINNET.
□ Запуск с mainnet-ключами требует явного подтверждения в конфиге:
  confirm_mainnet: true. Забыли — бот не стартует.
□ Первый запуск на mainnet — всегда $5 и минимальный размер,
  независимо от результатов бэктеста.
□ Жёсткие потолки зашиты в код и НЕ выносятся в конфиг:
  risk_per_trade ≤ 2%, daily_loss ≤ 10%, real_leverage ≤ 5x,
  max_positions ≤ 5. Конфиг сверх потолка обрезается с WARN.
□ Хэш риск-профиля пишется в лог при старте и в heartbeat.
□ Чек-лист перед запуском в ops/, проходится по пунктам.
```

## 10.8 Логи и приватность

- Логи не содержат: ключей, подписей, полного номера аккаунта, адресов вывода.
- Логи содержат: всё остальное, включая полные снимки решений — это нужно для разбора.
- Хранение: локально 90 дней, архив — 2 года, копия вне торгового сервера.
- Доступ к логам = доступ к вашей стратегии. Обращаться как с кодом.

## 10.9 Что логировать для расследования

- Все SSH-входы и изменения конфигурации.
- Хэш версии кода и хэш риск-профиля при каждом старте.
- Все ошибки авторизации и все HTTP 403.
- Все торговые действия с `orderLinkId`.
- Все переходы режима (`LIVE` → `MANAGE_ONLY` и т.д.) с причиной.
