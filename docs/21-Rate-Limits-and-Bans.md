# 🚦 21 · Лимиты запросов и защита от блокировки

> Это тот самый раздел, ради которого в исходном запросе была формулировка «защита от блокировки». В крипте она имеет буквальный технический смысл: **бот блокирует сам себя**, упираясь в лимиты биржи, и происходит это обычно в худший момент — когда рынок двигается и позиция открыта.

## 21.1 Типы блокировок и что их вызывает

| Тип | Кто блокирует | Симптом | Длительность |
|-----|--------------|---------|-------------|
| **Лимит по эндпоинту (UID)** | Bybit | `retCode 10006` — too many visits | секунды, скользящее окно |
| **Лимит по IP** | Bybit / CDN | HTTP 403, иногда без тела | минуты; при упорстве — дольше |
| **Расхождение часов** | Bybit | `retCode 10002` — invalid timestamp | до синхронизации часов |
| **IP не в белом списке ключа** | Bybit | `retCode 10010` / отказ авторизации | до исправления |
| **Истечение API-ключа** | Bybit | отказ авторизации | ключи без привязки к IP живут ограниченно |
| **Разрыв WebSocket** | сеть / биржа | тишина в потоке | до переподключения |
| **Ограничение аккаунта** | Bybit | отказ в торговле | до разбирательства |

Отдельно стоит последний пункт. Аккаунт может получить ограничение за **самоторговлю** — когда ваши же ордера матчатся друг с другом. Для бота, который одновременно держит лимитные заявки с двух сторон, это реальный риск, и он решается не «маскировкой», а тем, что робот **не выставляет пересекающихся собственных заявок** (см. 21.6).

## 21.2 Бюджет запросов как проектное ограничение

Лимиты Bybit заданы по UID и по эндпоинту, и они **не общие на всё**: на постановку ордера один лимит, на отмену другой, на чтение позиций третий. Точные значения берутся из документации и — что надёжнее — **из заголовков каждого ответа**:

```
X-Bapi-Limit                 предел для этого эндпоинта
X-Bapi-Limit-Status          сколько осталось в текущем окне
X-Bapi-Limit-Reset-Timestamp когда окно обнулится
```

**Требование к архитектуре:** робот не «надеется уложиться», а **ведёт учёт**. Каждый HTTP-клиент оборачивается в лимитер, который:

1. читает заголовки каждого ответа и обновляет локальную модель остатка;
2. не отправляет запрос, если остаток ниже резерва (по умолчанию 20% от лимита);
3. резерв **никогда не тратится на чтение** — он оставлен под аварийные действия: закрыть позицию, отменить ордер;
4. при `retCode 10006` переходит в backoff и помечает эндпоинт как остывающий;
5. при HTTP 403 останавливает **все** исходящие запросы на `BanCooldownSec` (по умолчанию 600 с) и поднимает алерт.

```
Приоритеты расходования бюджета (от высшего к низшему):
  P0  аварийное закрытие позиции, отмена ордера
  P1  постановка / изменение стопа
  P2  постановка входного ордера
  P3  сверка состояния (реконсиляция)
  P4  чтение справочной информации, статистика
```

При приближении к лимиту отключаются снизу вверх: сначала перестаёт опрашиваться статистика, и только в последнюю очередь — аварийные действия. Робот, который не может закрыть позицию, потому что истратил лимит на опрос баланса, — это дефект проектирования.

## 21.3 Главное правило: WebSocket вместо опроса

Большая часть блокировок возникает от того, что бот **опрашивает** REST в цикле. Это неправильная архитектура, независимо от лимитов.

| Данные | ❌ Как делают | ✅ Как надо |
|--------|-------------|-----------|
| Цены, стакан | `GET /v5/market/tickers` в цикле | WebSocket public: `orderbook.1`, `publicTrade`, `tickers` |
| Свои ордера | `GET /v5/order/realtime` в цикле | WebSocket private: `order` |
| Исполнения | опрос истории | WebSocket private: `execution` |
| Позиция | `GET /v5/position/list` в цикле | WebSocket private: `position` |
| Баланс | опрос | WebSocket private: `wallet` |
| Постановка ордера | REST | REST или **WebSocket Trade** (ниже задержка) |

**REST используется только для:** первичной загрузки состояния при старте, периодической сверки (раз в 30–60 с, не чаще), и торговых действий.

Это снижает расход лимита на два порядка и одновременно снижает задержку: событие приходит push-ом, а не через период опроса.

### Требования к WebSocket-слою

```
□ Ping каждые ~20 с, контроль pong; нет pong 2 раза подряд → реконнект
□ Реконнект с экспоненциальным backoff: 1, 2, 4, 8, 16, 30, 30... с джиттером
□ После реконнекта — ОБЯЗАТЕЛЬНАЯ полная сверка через REST:
  пока канал молчал, могло исполниться что угодно
□ Приватный поток: подпись с expires; переавторизация при реконнекте
□ Детект «тихого» сокета: нет ни одного сообщения дольше N сек
  при живом рынке → соединение считается мёртвым, даже если TCP открыт
□ Два независимых публичных соединения (данные) и приватное (аккаунт):
  падение одного не убивает другое
□ Последовательность обновлений стакана проверяется по seq/u;
  разрыв последовательности → пересинхронизация снапшотом
```

Последний пункт неочевиден и важен: инкрементальный стакан с пропущенным обновлением тихо расходится с реальностью, и робот начинает принимать решения по несуществующим ценам.

## 21.4 Синхронизация часов — причина внезапных отказов

Bybit отклоняет запрос, если его метка времени выходит за окно `recv_window` относительно времени сервера биржи. Симптом: бот работал месяц и вдруг перестал, ошибка «invalid timestamp».

```
□ NTP-синхронизация на хосте, проверка расхождения при старте
□ При старте: запрос /v5/market/time, вычисление offset = server - local
□ Offset применяется ко всем подписываемым запросам
□ Периодическая (раз в 5 мин) перепроверка offset
□ |offset| > 500 мс → WARN;  > 2000 мс → отказ от торговли и алерт
□ recv_window: 5000 мс. Больше ставить не надо — это ослабляет
  защиту от replay-атак, а проблему с часами не решает
```

## 21.5 Ключи API — конфигурация и защита

```
□ Права ключа: ТОЛЬКО «Trade» (Contract/Unified Trading).
  «Withdraw» — НИКОГДА. Ключ с правом вывода превращает любую утечку
  в потерю всех средств.
□ Привязка к IP обязательна: ключ работает только с IP вашего сервера.
  Это же продлевает срок жизни ключа.
□ Отдельные ключи: боевой (торговля), read-only (мониторинг и отчёты),
  testnet (разработка). Разные ключи — разные последствия утечки.
□ Ключ и секрет — в переменных окружения или в защищённом хранилище,
  НИКОГДА в коде, в git, в логах, в скриншотах.
□ .gitignore на .env с первого коммита, до того как туда попал секрет.
□ Логи: секрет и подпись маскируются. В лог пишется только префикс ключа.
□ Ротация ключа при любом подозрении и при смене исполнителя.
□ Отдельный субаккаунт Bybit под робота, если биржа это позволяет:
  ограничивает максимальный ущерб суммой на субаккаунте.
□ 2FA на аккаунте биржи; вывод — только на верифицированные адреса
  с задержкой (антифишинговые настройки Bybit).
```

> Ключ с правами торговли, но без вывода, при утечке позволяет злоумышленнику слить счёт через намеренно убыточные сделки. Это меньше, чем прямой вывод, но не «ничего». Поэтому IP-привязка обязательна, а не желательна.

## 21.6 Самоторговля и поведение, вызывающее ограничения

Что делать **нельзя** — не потому что «поймают», а потому что это ломает и счёт, и статистику:

| Поведение | Почему проблема |
|-----------|----------------|
| Одновременные собственные bid и ask, способные пересечься | Самоматчинг. Биржи отслеживают и ограничивают аккаунты |
| Шквал постановок/отмен без исполнений | Высокий order-to-trade ratio привлекает внимание риск-систем и жжёт лимиты |
| Постановка заведомо неисполнимых ордеров для «прощупывания» стакана | Манипулятивное поведение |
| Циклы «купил-продал» для накрутки объёма | Wash trading, прямое нарушение правил |
| Попытки обойти geo-ограничения или KYC | Вне области этого проекта. Замораживает средства и закрывает доступ |

**Что делает робот вместо этого:** держит не более одной активной заявки на сторону, отменяет заявку перед постановкой противоположной, считает и логирует order-to-trade ratio как метрику здоровья (целевое значение — ниже 20:1).

## 21.7 Идемпотентность через orderLinkId

Bybit поддерживает клиентский идентификатор ордера (`orderLinkId`). Это ключевой механизм защиты от дублей при потере ответа.

```
1. До отправки генерируем orderLinkId = детерминированный хэш
   (стратегия, символ, направление, метка времени решения, seq)
2. Отправляем ордер с этим orderLinkId
3. Ответ потерян / таймаут / разрыв:
     НЕ ретраим вслепую
     запрашиваем ордер по orderLinkId
     нашли → ордер существует, ретрая нет
     не нашли → безопасно повторить С ТЕМ ЖЕ orderLinkId
4. Повтор с тем же orderLinkId биржа отклонит как дубликат —
   это и есть страховка
```

Без этого механизма один потерянный ответ даёт две позиции вместо одной. Подробнее — [[07-Execution-Engine]].

## 21.8 Метрики здоровья, которые надо мерить

В телеметрию ([[13-Telemetry-and-Logging]]) добавляются:

| Метрика | Норма | Тревога |
|---------|-------|---------|
| Использование лимита по эндпоинту (пик за минуту) | < 50% | > 80% |
| Число `retCode 10006` за час | 0 | > 0 |
| Число HTTP 403 за сутки | 0 | ≥ 1 — инцидент |
| Расхождение часов с биржей | < 200 мс | > 500 мс |
| Реконнектов WS за сутки | < 10 | > 50 |
| Максимальная «тишина» в WS-потоке | < 5 с | > 30 с |
| Order-to-trade ratio | < 20 | > 50 |
| Разрывы последовательности стакана | 0 | > 0 |

## 21.9 Чек-лист «робот не заблокирует сам себя»

```
□ Все рыночные данные — через WebSocket, не через опрос REST
□ HTTP-клиент обёрнут в лимитер с учётом заголовков X-Bapi-Limit-*
□ Резерв лимита 20% не тратится на чтение
□ Приоритеты P0–P4 реализованы и протестированы под нагрузкой
□ Backoff экспоненциальный с джиттером, потолок и максимум попыток
□ HTTP 403 → полная остановка исходящих на 10 минут + алерт
□ Часы синхронизированы NTP, offset до биржи отслеживается
□ orderLinkId на каждом торговом действии
□ Один активный ордер на сторону, без самопересечения
□ Order-to-trade ratio логируется
□ Ключ: только Trade, привязан к IP, в переменных окружения
□ Проверено нагрузочным тестом на testnet: 1000 циклов
  постановка-отмена-исполнение без единого 10006 и 403
```
