# 🗄 23 · Данные: сбор, хранение, подготовка

> Решение по Q8 принято 18.09.2026: **бесплатные архивы Bybit для первой итерации + собственный сбор стакана, запущенный немедленно.** Обоснование и механика — здесь.

## 23.1 Почему сбор запускается раньше разработки бота

Стратегия входит **post-only лимитной заявкой**. Честно протестировать такую стратегию по свечам невозможно: свеча не знает, исполнилась бы ваша заявка на уровне или цена отскочила, не дойдя до него. Разница не косметическая — оптимистичное допущение «коснулось = исполнилось» превращает убыточную стратегию в прибыльную на бумаге ([[12-Testing-and-Validation]], 12.2).

История стакана нужна к началу фазы 2. Её нельзя докупить задним числом дёшево, но можно **накопить бесплатно**, если начать сегодня. Поэтому сбор — первая запущенная вещь в проекте, ещё до строчки кода бота.

```
Сегодня          запускаем collect_bybit.py
Через 2 месяца   начинается фаза 2 → данные уже есть
```

Стоимость решения: один процесс, ~65 МБ в сутки и дисциплина не выключать его.

## 23.2 Три источника, три роли

| Источник | Что даёт | Роль |
|----------|----------|------|
| **Архивы Bybit** (`public.bybit.com`) | тиковые сделки посуточно, глубина в годы, бесплатно | первая итерация фазы 2: проверка гипотезы «бывают ли движения ≥ 0.25%» |
| **Собственный сбор WS** | стакан L2 + лента ровно в той структуре, что в live | честная проверка post-only исполнения; накапливается с сегодня |
| **Платные провайдеры** | исторический L2 за годы | запасной вариант, если сроки поджимают сильнее бюджета |

**Логика такая:** архивы отвечают на вопрос «есть ли вообще что ловить» — на него можно ответить по сделкам, без стакана. Если ответ отрицательный, стакан не понадобится вовсе, и деньги на данные не потрачены. Если положительный — к этому моменту собственная база стакана уже накопится.

## 23.3 Сборщик

`research/collect_bybit.py` — публичные WS-потоки Bybit, API-ключ не нужен, ничего не торгует.

```bash
python research/collect_bybit.py --symbol XRPUSDT
```

Что пишет:

| Поток | Содержание | Частота |
|-------|-----------|---------|
| `*_trades_*.jsonl.gz` | каждая сделка: время биржи и локальное, сторона агрессора, цена, объём, id | всё, без прореживания |
| `*_book_*.jsonl.gz` | снимок топ-10 уровней с обеих сторон | раз в 200 мс (настраивается) |
| `*_meta_*.jsonl.gz` | старт/стоп, реконнекты, **разрывы последовательности стакана** | по событиям |

### Три решения в его конструкции

**1. Лента пишется целиком, стакан — прореживается.** Полный поток дельт стакана даёт объём, несоразмерный задаче, а для проверки исполнения post-only достаточно знать состояние верхних уровней с шагом в сотни миллисекунд. Сделки прореживать нельзя: это и есть настоящий order flow.

**2. Разрывы последовательности фиксируются явно.** Стакан, собранный из snapshot + delta с пропущенным обновлением, выглядит исправным и тихо врёт. Сборщик проверяет непрерывность `u` и при разрыве помечает себя рассинхронизированным, пишет событие и ждёт нового снимка. Периоды рассинхрона **исключаются из бэктеста**, а не используются молча.

**3. Буфер сбрасывается на диск каждые 5 секунд.** Незакрытый gzip нечитаем целиком. Без периодического сброса жёсткое завершение процесса теряет **весь текущий час**. При сборе, который идёт месяцами на меняющихся хостах (см. Q9), это не теоретический риск, а гарантированный.

**4. Файл никогда не открывается на дописывание.** Каждый запуск берёт свободное имя с суффиксом попытки: `..._07_r00.jsonl.gz`, `..._07_r01.jsonl.gz`. Причина — ниже, это найденный на практике дефект.

**5. Два сборщика по одному символу запуститься не могут.** Проверка свежести heartbeat при старте; обойти можно только явным `--force`.

### Дефект, найденный 19.09.2026, и почему он важен

Первая версия открывала часовой файл в режиме дописывания (`"at"`). Сценарий отказа:

```
1. Сборщик убит жёстко           → в файле оборванный gzip-член
2. Следующий запуск в тот же час → дописывает НОВЫЙ член после обрыва
3. Читатель доходит до обрыва    → "invalid block type"
4. Файл нечитаем ЦЕЛИКОМ         → потеряны и те часы, что писались успешно
```

Обнаружилось это не в теории: панель показывала ноль данных при живом сборщике и нулевых разрывах. Штатный `gzip.open` на файле падал так же, как самописный читатель, — значит, дело было в данных, а не в чтении.

Утверждение прошлой версии «переживает жёсткое убийство» оказалось верным лишь наполовину: записанное выживает **ровно до момента, пока в этот файл не дописали повторно**.

**Что исправлено:** режим `"wt"` и уникальное имя на каждый запуск. Теперь повреждение локально — пострадать может только хвост того файла, который писался в секунду падения, а все предыдущие файлы остаются целыми.

**Побочный вывод для фазы 1:** та же ошибка в торговом процессе стоила бы дороже. Правило «не дописывать в чужой поток» распространяется на `state.db`, логи и любой файл состояния. Защита от второго экземпляра — не бюрократия, а то, что предотвращает порчу данных двумя писателями.

### Три состояния файла и три разных исключения

Разбор дефекта дал ещё один результат: читатель встречает файлы в трёх состояниях, и наивный `gzip.open` падает на двух из трёх, теряя данные, которые на самом деле читаются.

| Состояние файла | Что бросает `gzip` | Данные до сбоя |
|-----------------|-------------------|----------------|
| Закрыт корректно | ничего | все |
| **Пишется прямо сейчас** | `EOFError` — нет маркера конца потока | **целы** |
| Процесс убит жёстко | `EOFError` | **целы** |
| Поток повреждён | `zlib.error: invalid block type` | **частично спасаемы** |

Поэтому всё чтение идёт через `research/gzio.py`. Он не бросает исключений на повреждённых данных, а возвращает записи **вместе с честным признаком** обрыва или порчи:

```
data/raw/XRPUSDT/
  XRPUSDT_trades_..._r00.jsonl.gz    2508 записей спасено · оборван
data/quarantine/
  XRPUSDT_trades_20260919_07.jsonl.gz  584 записей спасено · ПОВРЕЖДЁН
```

Из повреждённого файла удалось вытащить 265 снимков стакана и 584 сделки — они были бы потеряны целиком при наивном чтении.

**Принцип, который из этого следует:** потеря данных должна быть **измеренной, а не случайной**. Молча вернуть 80% строк и сделать вид, что это всё, — худший из вариантов: статистика поедет, а причина не найдётся. Поэтому карта дыр (`gaps.parquet`) — обязательный артефакт ETL, а не приложение к нему.

```bash
python research/gzio.py data/raw/XRPUSDT     # отчёт по каталогу
```

### Объём хранения (замер на XRPUSDT)

```
сделки:  ~30 байт/запись сжатой,  ~15 сделок/с → ~40 МБ/сутки
стакан:  ~60 байт/снимок сжатого,  5 снимков/с → ~25 МБ/сутки
                                                 ───────────
                                                 ~65 МБ/сутки
```

При активном рынке — до ~120 МБ/сутки. Ориентир: **2–3.5 ГБ в месяц, 25–40 ГБ в год**. Помещается на любой дешёвый диск; но дисковый монитор из [[09-Reliability-and-State]] обязателен.

## 23.4 Непрерывность при смене хоста

Q9: хостинг «абсолютно разный и всегда может меняться». Для сборщика это значит:

```
□ Процесс перезапускаемый и без состояния между запусками:
  вся история — в файлах, ничего в памяти дольше часа.
□ Ротация по часам UTC: при переезде теряется максимум текущий час,
  и он остаётся читаемым благодаря периодическому сбросу буфера.
□ Каталог data/raw/ — единственное, что нужно перенести.
□ Пропуск в данных — это НЕ «плохие данные», а факт, который должен
  быть записан. Периоды простоя фиксируются в meta-потоке и
  исключаются из бэктеста.
□ Никаких допущений о путях, часовом поясе хоста и правах: всё
  относительно рабочего каталога, всё время в UTC.
```

**Рекомендация:** сборщик — единственный компонент, которому стоит дать постоянное место. Он не торгует, не держит ключей, ему нужен лишь диск и сеть. Самый дешёвый VPS за пару долларов в месяц решает задачу и одновременно даёт стабильный IP, который понадобится для ключа биржи ([[15-Deployment-and-Ops]], 15.2).

## 23.5 Конвейер подготовки

```
data/raw/<SYMBOL>/*.jsonl.gz          сырой захват, как пришло с биржи
     │  research/etl.py
     │    • валидация схемы (падает при несовпадении, не пропускает молча)
     │    • дедупликация сделок по id
     │    • проверка монотонности времени
     │    • разметка периодов рассинхрона и простоя
     │    • Decimal → фиксированная точность
     ▼
research/data/<SYMBOL>/trades.parquet
research/data/<SYMBOL>/book.parquet
research/data/<SYMBOL>/gaps.parquet   ← карта дыр, обязательный артефакт
     │  research/backtest/
     ▼
research/runs/<run_id>/
```

Сырой захват **никогда не перезаписывается**. Любая ошибка ETL исправляется повторным прогоном из сырья; если сырьё модифицировано, восстановить нечего.

## 23.6 Проверка качества (`research/check_data.py`, фаза 2)

Выполняется до любого бэктеста, выдаёт:

- покрытие по суткам: сколько часов реально записано против календаря;
- карту пропусков и периодов рассинхрона;
- распределение межсделочных интервалов (аномалии = проблемы сбора);
- долю дубликатов по id;
- распределение спреда по часам UTC — оно же даёт суточный профиль активности;
- выбросы цены > 10σ;
- сверку собственного захвата с архивами Bybit на пересекающемся отрезке.

Последний пункт важен: он отвечает, не теряет ли ваш сборщик данные. Расхождение по числу сделок более чем на 0.5% — дефект сбора, а не «бывает».

## 23.7 Что запустить прямо сейчас

```bash
# 1. окружение (один раз)
python -m venv .venv
.venv/Scripts/pip install websockets requests

# 2. сбор — и не выключать
.venv/Scripts/python research/collect_bybit.py --symbol XRPUSDT
```

Проверка, что всё идёт: в выводе каждые 5 минут строка вида

```
аптайм 3.20 ч · сделок 172431 · снимков 57600 · разрывов 0 · реконнектов 1 · синхронизирован: да
```

`разрывов 0` и `синхронизирован: да` — то, что должно быть. Растущее число разрывов означает проблему сети или нагрузки на хост.
