# 🔎 11 · Качество исполнения

> «Кажется, что-то испортилось» — это не гипотеза, а отсутствие измерений. Здесь описано, как превратить ощущение в число и что с числом делать.

## 11.1 Почему это отдельная подсистема

У скальпинга есть свойство: он одинаково чувствителен к ухудшению исполнения и к ухудшению сигнала, но **выглядит это одинаково** — эквити перестаёт расти. Без телеметрии исполнения вы будете чинить стратегию, когда проблема в исполнении, или наоборот. Обе ошибки дорогие.

В крипте, в отличие от форекса, у биржи нет мотива «играть против вас»: Bybit зарабатывает комиссию, а не на вашем убытке, и матчинг централизован. Поэтому вопрос ставится иначе: не «честна ли биржа», а **«реализуем ли мы заложенную в модель экономику»**. Главный вопрос: действительно ли мы исполняемся мейкером, или робот втихую платит вдвое.

## 11.2 Метрики

Считаются из `exec.csv`, агрегируются по суткам, часам UTC и стороне сделки.

| Метрика | Определение | Цель | Тревога |
|---------|------------|------|---------|
| **Maker ratio** | доля исполнений с `is_maker = true` | **> 80%** | < 60% |
| **Post-only reject rate** | доля post-only заявок, отклонённых из-за пересечения | 10–30% — норма | > 50%: уровни ставятся слишком агрессивно |
| **Post-only fill ratio** | доля выставленных post-only, дошедших до исполнения | > 50% | < 30%: сигналы теряются |
| **Средняя комиссия, bps** | `fee / notional × 10 000` | ≈ 3.75 (при 80% maker) | > 5.0 |
| **Факт C_total / модель** | реальные издержки против заложенных | 0.8–1.2 | > 1.3 две недели |
| **Проскальзывание taker-выходов** | `(fill − ref) / ref × 10 000`, со знаком | ≈ 0 ± 1 bps | медиана хуже −2 bps |
| **RTT p50 / p95 / p99** | `ts_reply − ts_send` | 30 / 120 / 300 мс | p95 > 500 мс |
| **WS lag** | `local_ts − exchange_ts` в сообщениях | < 50 мс | > 200 мс |
| **Fill rate** | доля запросов с `retCode = 0` | > 99% | < 97% |
| **Order-to-trade ratio** | ордеров на одно исполнение | < 20 | > 50 |
| **Уплаченный фандинг за период** | сумма | ≈ 0 | заметная доля PnL → тайм-логика сломана |
| **Использование лимита** | пик за минуту | < 50% | > 80% |

### Maker ratio — главная метрика

Вся экономика стратегии построена на предположении, что вход исполняется мейкером (2.0 bps) вместо тейкера (5.5 bps). Если фактический maker ratio упал с 80% до 40%, издержки выросли с 7.5 до 9.2 bps, то есть на 23% — и это может съесть весь эдж, не изменив ни одного сигнала.

Причины падения, в порядке вероятности:

1. уровни post-only ставятся слишком близко к рынку → отклонения → fallback на taker;
2. волатильность выросла, цена уходит раньше исполнения;
3. логика fallback слишком легко переключается на taker — порог надо ужесточить;
4. изменился режим рынка, и сетап стал требовать немедленного входа.

## 11.3 Процедура разбора «исполнение или сигнал»

```
Эквити перестало расти
        │
        ├─ Факт C_total / модель > 1.3 ?
        │      ├─ ДА → проблема в исполнении
        │      │      ├─ Maker ratio упал?         → уровни / fallback
        │      │      ├─ RTT / WS lag выросли?     → сеть, регион VPS
        │      │      ├─ Фандинг съедает PnL?      → тайм-логика выходов
        │      │      ├─ Комиссионный уровень      → пересчитать CostGate
        │      │         изменился?
        │      │      └─ Проскальзывание выходов   → размер позиции
        │      │         выросло?                     против глубины стакана
        │      └─ НЕТ → проблема в сигнале
        │             ├─ Winrate упал, RR держится  → сменился режим рынка
        │             ├─ RR упал, winrate держится  → волатильность сжалась
        │             └─ Оба упали                  → эдж исчез / переобучение
        └─ Сравнить с эталонным прогоном бэктеста на том же периоде
```

Последняя строка — самый надёжный инструмент: прогнать бэктест на том же отрезке, что отработал live, и сравнить не прибыль, а **распределения**: время удержания, maker ratio, ширину стопов, долю выходов по каждой причине. Расхождение сразу указывает, какой блок разошёлся с моделью.

## 11.4 Latency-бюджет и география

| Локация VPS | Типичный RTT до Bybit | Пригодность |
|-------------|----------------------|-------------|
| Сингапур / AWS ap-southeast-1 | **5–20 мс** | целевая |
| Токио, Гонконг | 30–60 мс | хорошо |
| Франкфурт, Лондон | 150–250 мс | приемлемо для холдов в минуты |
| Москва / СНГ | 200–350 мс | приемлемо, но хуже |
| Домашний компьютер | 250–500 мс + нестабильность | **только для разработки** |

Для стратегии с целями 25+ bps и удержанием в минуты разница между 20 и 250 мс не критична — цена за 250 мс на XRPUSDT сдвигается на доли bps. Она становится критичной, если стратегия эволюционирует в маркет-мейкинг.

**Практический порядок:** сначала замерить фактический RTT из предполагаемой локации (`research/latency_probe.py`, фаза 0), потом решать. Платить за сингапурский VPS, если холд составляет 10 минут, смысла нет.

## 11.5 Сравнение площадок (когда это понадобится)

Если возникнет вопрос «а не лучше ли на другой бирже», сравнивать надо не «где комиссия ниже», а суммарную стоимость:

```
C_total = комиссия_maker + комиссия_taker + спред + проскальзывание
        + стоимость недоисполнения post-only (пропущенные сигналы)
```

И отдельно — доступность инструмента при вашем капитале (минимальный ордер), качество API, наличие исторических данных нужной глубины, стабильность.

Метод: один и тот же бот в режиме `SIGNAL_ONLY` подключается к двум площадкам параллельно и пишет, **какие сделки он бы совершил и по каким ценам**. Через 2–4 недели сравниваются распределения издержек. Это дешевле, чем заводить капитал на вторую площадку.

## 11.6 Еженедельный отчёт

Автоматически, в `research/reports/exec_<date>.html`:

1. Maker ratio по дням и по часам UTC.
2. Гистограмма post-only: выставлено / отклонено / исполнено / отменено.
3. Фактическая комиссия в bps против модельной, тренд.
4. Проскальзывание taker-выходов, распределение.
5. RTT и WS lag: перцентили по дням.
6. Использование лимитов, число `10006` и 403.
7. Уплаченный фандинг, разбивка по сделкам.
8. Таблица `retCode` с долями.
9. Итоговый вердикт: реализуется ли заложенная экономика.
