# ⚡ 07 · Движок исполнения (Bybit V5)

> Самая скучная и самая дорогая подсистема. Ошибка здесь не «уменьшает прибыль» — она создаёт вторую позицию там, где должна быть одна, или оставляет позицию без стопа.

## 7.1 Единственная точка отправки

Все торговые действия проходят через `OrderRouter`. Прямые вызовы REST-клиента из других модулей запрещены и ловятся ревью. Причина: идемпотентность, бюджет лимитов и телеметрия должны быть в одном месте, иначе они не работают нигде.

```
TradePlan ──▶ IdempotencyGuard ──▶ Validator ──▶ RateLimiter ──▶ Bybit
                    │                  │              │            │
             orderLinkId         qtyStep/tick     приоритет P0-P4  │
                    │            minNotional                       │
                    │◀──────────── reconcile ◀─────────────────────┘
                    ▼
             ErrorClassifier(retCode)
                    │
      ┌─────────────┼──────────────┬───────────────┐
      ▼             ▼              ▼               ▼
   RETRY        RECALC          FATAL           SUCCESS
 (тот же      (пересчёт      (стоп + алерт)   (учёт, метрики)
  план)        qty/price)
```

## 7.2 Идемпотентность через `orderLinkId`

**Факт, ломающий наивные реализации:** таймаут запроса и разрыв соединения **не означают, что ордер не исполнен**. Он мог дойти до биржи и сработать, а ответ потеряться. Слепой ретрай в этой ситуации открывает вторую позицию — на депозите $5 это означает отказ по марже, на большом депозите двойной риск.

Bybit даёт клиентский идентификатор ордера. Протокол:

```
1. ДО отправки: orderLinkId = f(strategy_id, symbol, side, decision_ts, seq)
   детерминированный, уникальный, ≤ 36 символов
   записывается в локальный журнал ДО сетевого вызова

2. Отправка ордера с этим orderLinkId

3. Ответ retCode = 0:
      commit(orderLinkId → orderId), дальше работаем по orderId

4. Таймаут / разрыв / неизвестная ошибка:
      НЕ РЕТРАИТЬ.
      Состояние PENDING_UNKNOWN.
      В течение ReconcileWindowSec (по умолчанию 10 с), с интервалом 1 с:
        GET /v5/order/realtime?orderLinkId=...   (активные)
        GET /v5/order/history?orderLinkId=...    (исполненные/отменённые)

      Исход сверки ТРЁХЗНАЧНЫЙ, а не двузначный:
        ордер найден              → commit, повтора нет
        сверка прошла, ордера нет → повтор С ТЕМ ЖЕ orderLinkId
        СВЕРКА НЕ ПРОШЛА         → повтора НЕТ, запись остаётся открытой,
                                    торговля останавливается

5. Никогда не генерировать новый orderLinkId для повтора той же операции
```

> ⚠️ **Дефект, найденный при реализации 19.09.2026.** Первая версия роутера возвращала из сверки `order_id | None` — то есть путала «ордера нет» и «не удалось спросить». Если связь оборвана настолько, что не проходит и запрос отправки, и запрос проверки, то отсутствие ответа трактовалось как отсутствие ордера, и роутер повторял отправку — создавая ровно тот дубль, ради предотвращения которого написан весь механизм.
>
> Исправлено: сверка возвращает пару `(order_id, проверено_ли)`. При `проверено_ли = False` повтор не выполняется ни при каких условиях, запись остаётся в состоянии `UNKNOWN`, бот переходит в `MANAGE_ONLY`. Открытый вопрос к бирже закрывается следующим циклом реконсиляции или при старте процесса.
>
> Покрыто тестом `tests/test_router.py::TestIdempotency::test_failed_reconciliation_never_retries`.

Дополнительный контур: приватный WebSocket-канал `order` присылает подтверждение раньше, чем приходит REST-ответ. Если подтверждение по нашему `orderLinkId` уже получено по WS — REST-ответ игнорируется как устаревший.

## 7.3 Классификация ошибок

Bybit возвращает `retCode` в теле ответа; HTTP-код при этом может быть 200. Проверять надо **оба**.

| Класс | Признаки | Действие |
|-------|---------|---------|
| **OK** | `retCode = 0` | commit |
| **RATE** | `10006` (too many visits), `10018` (IP rate limit), HTTP 429 | backoff по [[21-Rate-Limits-and-Bans]], пометить эндпоинт остывающим |
| **BAN** | HTTP 403 | **полная остановка исходящих** на `BanCooldownSec`, алерт, переход в `MANAGE_ONLY` |
| **CLOCK** | `10002` (timestamp / recv_window) | пересинхронизировать offset, один повтор; повтор неудачен → `PAUSED` |
| **AUTH** | `10003` ключ, `10004` подпись, `10005` права, `10010` IP не совпал | FATAL. Ретраи бессмысленны и вредны — это конфигурация |
| **UNKNOWN** | таймаут, разрыв TCP, HTTP 5xx | **реконсиляция** по 7.2, не ретрай |
| **RECALC** | ошибки параметров ордера: некратное `qtyStep` количество, цена вне `tickSize`, номинал ниже `minNotionalValue`, нарушение `reduceOnly` | пересчитать и один повтор; второй отказ → FATAL |
| **FUNDS** | недостаточно баланса / маржи | FATAL для этой сделки, не для бота: залогировать, пропустить сигнал; при повторении → `MANAGE_ONLY` |
| **STATE** | ордер не найден, уже отменён, позиция уже закрыта | SOFT: синхронизировать локальное состояние, не ошибка |
| **MAINT** | биржа на техработах, инструмент не в статусе `Trading` | SOFT: пауза до восстановления |

> ⚠️ Полная числовая таблица `retCode` строится из актуальной документации Bybit **и проверяется мок-биржей**: на каждый код должен быть тест, доказывающий, что робот идёт по нужной ветке. Коды меняются и добавляются — поэтому в коде классификация идёт по таблице соответствия, а неизвестный код по умолчанию трактуется как **UNKNOWN**, то есть запускает реконсиляцию, а не ретрай. Неизвестная ошибка никогда не должна молча приводить к повтору.

**Общие правила ретраев:** не более 3 попыток на действие, суммарный бюджет ≤ 5 с, backoff экспоненциальный с джиттером (100 / 300 / 900 мс ± 30%), ретраи — в асинхронной задаче, не блокируя обработку рыночных данных.

## 7.4 Типы ордеров и режим исполнения

| Задача | Тип ордера | Параметры |
|--------|-----------|----------|
| Вход мейкером (основной) | `Limit` | `timeInForce: PostOnly` — гарантирует комиссию maker; если заявка пересечёт стакан, она **отклоняется**, а не исполняется тейкером |
| Вход тейкером (fallback) | `Market` или `Limit` IOC | только если сигнал критичен по времени и `CostGate` это допускает |
| Стоп-лосс | `stopLoss` на позиции | серверный, живёт на бирже |
| Тейк-профит | `takeProfit` на позиции | серверный |
| Выход по сигналу | `Market` + `reduceOnly: true` | `reduceOnly` защищает от случайного открытия противоположной позиции |
| Аварийный выход | `Market` + `reduceOnly: true` | приоритет P0 в бюджете лимитов |

**Про PostOnly.** Отклонение post-only заявки — это **нормальный рабочий исход**, а не ошибка. Он означает «цена ушла, вход по задуманной цене невозможен». Правильная реакция — пересчитать уровень и, если сигнал ещё валиден и `CostGate` проходит, выставить заново; максимум `PostOnlyRetries` раз (по умолчанию 2), после чего сигнал считается пропущенным. Логируется отдельным кодом, метрика `post_only_reject_rate` — в телеметрию.

**Про режим позиции.** Bybit поддерживает one-way и hedge mode. Для v1 — **one-way**, принудительно, с проверкой при старте: hedge mode на одном символе усложняет учёт без всякой пользы для одной стратегии.

## 7.5 Стоп-лосс — обязателен и обязателен на бирже

```
1. Стоп ставится вместе с открытием позиции (поле stopLoss в запросе),
   либо немедленно после подтверждения открытия
2. Подтверждение обязательно: после исполнения входа проверяем,
   что у позиции реально установлен stopLoss (WS-канал position
   или GET /v5/position/list)
3. Стоп не установлен → 3 попытки выставить
4. Не удалось → АВАРИЙНОЕ ЗАКРЫТИЕ позиции по рынку + алерт
```

Пункт 4 не обсуждается. Позиция без стопа на инструменте с 5% дневной волатильностью и плечом — это неограниченный риск, и обнаружиться он должен за секунды, а не когда вы откроете ноутбук.

**Локальный дублирующий стоп** допустим как *дополнительный*, более близкий уровень, исполняемый ботом. Он **не заменяет** биржевой: бот может упасть, биржа — нет.

## 7.6 Контроль качества исполнения

На каждое действие пишется строка в `exec.csv`:

```
ts_send, order_link_id, action, symbol, side, order_type, tif,
qty_req, price_req, bid, ask, mid, spread_bps,
ret_code, ret_msg, ts_reply, rtt_ms,
qty_filled, price_fill, fee_paid, fee_rate_bps, is_maker,
slippage_bps, sl_set, tp_set, attempt_no,
limit_used_pct, ws_lag_ms
```

Поля `is_maker` и `fee_rate_bps` — ключевые: они показывают, действительно ли реализуется целевая экономика из [[04-Microstructure-and-Costs]], или робот втихую исполняется тейкером и платит вдвое.

## 7.7 Гейты перед любой отправкой

```python
def can_trade() -> bool:
    return (
        mode is LIVE
        and ws_public.is_alive()        # рыночные данные свежие
        and ws_private.is_alive()       # аккаунт синхронизирован
        and orderbook.in_sync()         # нет разрыва последовательности
        and clock.offset_ms < 500       # часы согласованы с биржей
        and rate_limiter.has_budget(P2) # хватает бюджета запросов
        and not ban_cooldown.active()
        and instrument.status == "Trading"
        and reconciliation.ok()         # локальное состояние = биржа
        and tick_age_ms < MAX_TICK_AGE
    )
```

Каждый провалившийся гейт логируется **своим кодом**. «Робот не торгует» — это вопрос, на который лог обязан отвечать за одну секунду.

## 7.8 Размер ордера: арифметика без ошибок

```python
from decimal import Decimal, ROUND_DOWN

def normalize_qty(raw: Decimal, step: Decimal, min_qty: Decimal,
                  price: Decimal, min_notional: Decimal) -> Decimal | None:
    qty = (raw / step).to_integral_value(rounding=ROUND_DOWN) * step
    if qty < min_qty:
        return None                      # НЕ округлять вверх
    if qty * price < min_notional:
        return None                      # сделка невозможна — не торгуем
    return qty
```

Два правила, нарушение которых стоит денег:

1. **Округление только вниз.** Округление вверх молча превышает заданный риск.
2. **Не дотягиваем до минимума.** Если расчётный объём ниже минимального — сделка пропускается и логируется. «Ну поставим минимум» — это торговля с неизвестным риском.

Вся арифметика — `Decimal`. `float` здесь не «менее точен», он **неверен**: количество, не кратное `qtyStep` из-за представления двоичной дробью, отклоняется биржей.

## 7.9 Тесты движка исполнения (обязательные, на мок-бирже)

1. 1000 отправок с инжекцией каждого класса ошибок из 7.3 → ни одной дублирующей позиции, ни одной необработанной ветки.
2. Таймаут + реально исполненный ордер → реконсиляция находит его по `orderLinkId`, ретрая нет.
3. Таймаут + неисполненный ордер → ровно один повтор с тем же `orderLinkId`.
4. Повтор с существующим `orderLinkId` → отклонён биржей, обработан корректно.
5. PostOnly отклонён 3 раза подряд → сигнал помечен пропущенным, не зациклился.
6. Вход исполнен, стоп не установлен → аварийное закрытие в пределах 3 с.
7. HTTP 403 → все исходящие остановлены, алерт, `MANAGE_ONLY`.
8. Расхождение часов 3 с → отказ от торговли, ресинхронизация, восстановление.
9. Разрыв WS во время открытой позиции → после реконнекта полная сверка, состояние верное.
10. Объём ниже `minNotionalValue` → отказ от сделки, а не отправка невалидного запроса.
11. Частичное исполнение → риск и сопровождение пересчитаны по фактическому объёму.
12. Нагрузочный: 1000 циклов постановка-отмена без единого `10006`.
