# 📊 13 · Телеметрия и логи

> Правило: **каждое решение робота должно быть восстановимо из логов без запуска отладчика.** Если после инцидента нужно «повторить и посмотреть» — телеметрия спроектирована плохо.

## 13.1 Уровни логирования

| Уровень | Что попадает | В live | В бэктесте | В оптимизации |
|---------|-------------|--------|-----------|---------------|
| `FATAL` | торговля остановлена | ✅ + алерт | ✅ | ✅ |
| `ERROR` | отказ операции, требующий внимания | ✅ + алерт | ✅ | ❌ |
| `WARN` | аномалия без остановки | ✅ | ✅ | ❌ |
| `TRADE` | открытие/закрытие/модификация | ✅ | ✅ | в parquet |
| `DECISION` | почему вошли / почему НЕ вошли | ✅ | ✅ | ❌ |
| `DEBUG` | внутренние значения | по флагу | по флагу | ❌ |

В режиме оптимизации любой файловый вывод отключается полностью: при переборе тысяч конфигураций логирование становится узким местом и забивает диск.

Формат — **JSON-строки** (`structlog`), а не свободный текст: логи разбираются скриптами, а не только глазами.

## 13.2 Формат события

```json
{"ts":"2026-09-18T14:32:17.482Z","mode":"LIVE","level":"DECISION",
 "module":"aggregator","code":"NO_ENTRY","symbol":"XRPUSDT","side":"LONG",
 "score":0.61,"threshold":0.55,"agree":3,
 "veto":"COST","edge_bps":18.4,"cost_bps":8.2,"k":3.0,"need_bps":24.6,
 "spread_bps":0.74,"atr_bps":31.2,"regime":"TREND",
 "book_imbalance":0.22,"tape_aggression":0.31,
 "data_age_ms":38,"sec_to_funding":4120}
```

Обязательные поля любого события: `ts` (UTC, мс), `mode`, `level`, `module`, `code`.
Для `DECISION` дополнительно — полный снимок входов, достаточный для воспроизведения решения без отладчика.

**Отказы логируются наравне с действиями.** Лог, в котором видно только совершённые сделки, бесполезен: главный вопрос при разборе — «почему робот НЕ вошёл там, где должен был».

## 13.3 Схема `trades.csv`

Одна строка на закрытую сделку. Поля (минимум):

```
trade_id, order_link_id, strategy_id, symbol, side, setup, regime,
open_ts_ms, entry_order_type, entry_is_maker, entry_price_ref,
entry_price_fill, entry_slippage_bps, post_only_attempts,
sl_price, tp_price, sl_bps, rr_planned,
qty, notional, risk_usdt, risk_pct, real_leverage,
score, votes_json, vetoes_checked_json,
spread_open_bps, atr_open_bps, book_imbalance_open, tape_aggression_open,
close_ts_ms, close_price, close_reason, close_is_maker, hold_sec,
qty_closed, partial_count,
mfe_bps, mae_bps, mfe_r, mae_r,
gross_pnl, fee_paid, fee_bps, funding_paid, net_pnl, net_r,
exec_attempts, rtt_ms_avg, ws_lag_ms_avg,
equity_before, equity_after, daily_pnl_after,
code_version, cfg_hash, exchange, testnet, account_masked
```

`votes_json` — голоса всех детекторов на момент входа. Без них невозможно постфактум спросить «а какой детектор на самом деле зарабатывает».

`entry_is_maker` / `close_is_maker` / `fee_bps` — ключевые: они показывают, реализуется ли заложенная экономика или бот втихую платит taker-комиссию вдвое.

## 13.4 Метрики, считаемые роботом онлайн

Обновляются в памяти, сбрасываются в heartbeat и на панель:

| Группа | Метрики |
|--------|---------|
| Сутки (UTC) | сделок, winrate, net PnL (%), просадка от дневного пика, серия убытков |
| Скользящее окно (50 сделок) | expectancy в R, PF, **maker ratio**, средняя комиссия в bps, средний спред входа |
| Исполнение | fill rate, post-only reject/fill ratio, RTT p50/p95, WS lag |
| Здоровье | uptime, возраст данных, реконнектов WS, использование лимитов, число 403 и 10006, offset часов |
| Риск | реальное плечо, использование маржи, дистанция до ликвидации, `risk_factor`, уплаченный фандинг |

## 13.5 Панель оператора

Панель — это консольный вывод (TUI) или простая веб-страница, читающая `heartbeat.json`. Она **не является частью торгового процесса**: отрисовка не должна занимать его цикл событий.

## 13.6 Алерты

| Событие | Срочность |
|---------|----------|
| `FATAL`, переход в `PAUSED` | немедленно |
| **HTTP 403 / бан по лимитам** | немедленно |
| Позиция без биржевого стопа | немедленно |
| Реконсиляция не сошлась | немедленно |
| Дневной лимит достигнут | немедленно |
| Расхождение часов > 2 с | немедленно |
| Оба WS мертвы > 60 с | немедленно |
| Просадка > 10% | в течение минуты |
| Maker ratio упал ниже 60% | ежедневный дайджест |
| Деградация издержек (`факт/модель > 1.3`) | ежедневный дайджест |
| Спецификации инструмента изменились | немедленно |
| Дневной итог | 1 раз в сутки |
| Еженедельный отчёт | 1 раз в неделю |

**Анти-спам:** одинаковые алерты схлопываются по `dedup_key` с окном 5 минут и счётчиком повторов. Бот, заваливающий оператора сообщениями, обучает их игнорировать — и следующий важный алерт будет пропущен.

### Канал: Telegram, через отдельный агент

`ops/alert_agent.py` — готов. Торговый бот **не знает про Telegram** и не держит токен: он кладёт JSON-файл в `data/alerts/`, агент забирает, отправляет и переносит в `sent/` или `failed/`.

```json
{"ts_ms": 1789751528905, "level": "FATAL",
 "title": "Позиция без стопа",
 "text": "XRPUSDT LONG 3.6 — стоп не выставлен после 3 попыток",
 "dedup_key": "no_sl_XRPUSDT"}
```

Три причины такого разделения:

1. **Сетевой вызов к Telegram может зависнуть на десятки секунд.** Внутри торгового процесса это означает, что на время зависания не обрабатываются котировки и не двигаются стопы.
2. **Токен — секрет.** Он не должен лежать в окружении процесса, который ходит на биржу с торговым ключом: одна утечка не должна давать обе вещи сразу.
3. **Падение канала алертов не должно ронять торговлю**, и наоборот.

Свойства агента: интервал между сообщениями ≥ 1.5 с (заметно ниже лимита Telegram — упереться в ограничение именно в момент инцидента недопустимо); ретраи с нарастающей паузой; неотправленное сообщение **не выбрасывается**, а перекладывается в `failed/`, где его видно глазами.

Настройка — `ops/.env.example`, проверка — `python ops/alert_agent.py --test`.

### Проверено 19.09.2026

| Сценарий | Результат |
|----------|-----------|
| Доставка 5 алертов разных уровней | ✅ все доставлены, форматирование корректно |
| Telegram отвечает 429 на каждый запрос | ✅ 4 повтора с нарастающей паузой, затем `failed/` |
| Сообщение после исчерпания попыток | ✅ **не потеряно**, история попыток и текст ошибки сохранены в файле |
| Панель показывает недоставленные | ✅ счётчик + пометка «РАЗОБРАТЬ» |

Проверка выполняется против `ops/mock_telegram.py` — локальной заглушки API. Она умеет возвращать 429 и задерживать ответ, то есть воспроизводит ветки, которые на живом Telegram вызвать трудно. Живой токен для этого не нужен:

```bash
python ops/mock_telegram.py --port 8081 --fail-rate 1.0
CASHMASH_TG_API_BASE=http://127.0.0.1:8081 python ops/alert_agent.py --once
```

## 13.6б Панель оператора: `ops/status.py`

Читает **только** heartbeat-файлы и каталоги данных. Ни одного запроса к бирже, никакой зависимости от торгового процесса: панель не должна ни тормозить его, ни падать вместе с ним, а при мёртвом процессе обязана это показать, а не зависнуть.

```
┌──────────────────────────────────────────────────────────┐
│ CashMash · сборщик ● РАБОТАЕТ                            │
│ XRPUSDT · Bybit · MAINNET                                │
├──────────────────────────────────────────────────────────┤
│ Аптайм        0:01:07         Стакан      да             │
│ Сделок        638             Снимков     281            │
│ Разрывов      0               Реконнект   0              │
│ Bid/Ask       1.4195 / 1.4196 Спред       0.70 bps       │
│ Возраст тика  15 мс                                      │
├──────────────────────────────────────────────────────────┤
│ Сырьё WS      74 КБ / 6 ф.    Бары        10 МБ / 21     │
│ Темп сбора    92 МБ/сут                                  │
├──────────────────────────────────────────────────────────┤
```

```bash

```

## 13.6в Веб-панель: `ops/dashboard.py`

### Тонкий или толстый клиент — и почему это не тот выбор

Вопрос обычно ставят как «терминал или веб». Правильная ось другая: **сколько прав у панели по отношению к торговому процессу.**

| Вариант | Права | Вердикт |
|---------|-------|---------|
| Панель внутри торгового процесса (общий поток, общая память) | полные | ❌ Отрисовка тормозит торговый цикл, падение панели роняет торговлю |
| Панель ходит на биржу сама | читает рынок | ❌ Тратит бюджет лимитов API, который зарезервирован под аварийные действия ([[21-Rate-Limits-and-Bans]]) |
| **Панель читает только файлы и БД** | чтение локальных данных | ✅ **выбрано** |

Оба наших клиента — и терминальный, и веб — относятся к третьей строке. Веб-панель богаче визуально, но по правам она такая же: не может отдать ни одной команды, не знает ключей, не делает ни одного сетевого запроса к бирже. Торговый процесс о её существовании не знает и не тратит на неё ни микросекунды.

**Управление осознанно вынесено из панели.** Команды идут через kill-switch с HMAC-подписью ([[10-Security]], 10.7), а не через кнопку в веб-интерфейсе, открытом на localhost. Панель показывает, но не трогает.

### Что показывает

| Блок | Источник | Статус |
|------|----------|--------|
| Средняя цена за 3 минуты, изменение в bps, средний спред | снимки стакана | ✅ |
| Стакан: 10 уровней с объёмами | снимки стакана | ✅ |
| Поток сделок за минуту (агрессия покупателей против продавцов) | лента | ✅ |
| Лента сделок с направлением | лента | ✅ |
| Состояние сбора: синхронность, разрывы, реконнекты, возраст данных | heartbeat | ✅ |
| Алерты: очередь, отправленные, недоставленные | каталог очереди | ✅ |
| **Средства кошелька: сколько денег на счету и откуда это известно** | heartbeat торгового процесса, протокол проверки ключа | ✅ |
| **Решения робота: сигнал, скор, сработавшие вето** | `state.db` | ✅ |
| **Реальные сделки: открытая позиция, закрытые сделки, заявки в полёте, итог** | `state.db` | ✅ |
| Виртуальные сделки: журнал и проверка допущений | `data/paper/` | ✅ |

Последние строки — то, ради чего панель и делается. Пока торгового процесса нет, блок честно пишет «не развёрнут» и перечисляет, что там появится. Рисовать нули, неотличимые от настоящих, нельзя: оператор, привыкший к пустой таблице, не заметит, когда она останется пустой из-за отказа.

### Кошелёк: число и его происхождение

Баланс приходит из двух источников разного качества, и смешивать их нельзя. Торговый процесс получает его по приватному потоку биржи — это живое число. Проверка ключа знала его на момент проверки — это число с датой. Панель всегда называет источник и возраст: «4.91 USDT» без даты читается как «сейчас», а может быть трёхчасовой давности.

Ноль сюда не пишется никогда. Когда процесс работает, а счёт не видит (ключ не подошёл, контуры разошлись), ноль выглядел бы как измерение — как пустой кошелёк. Панель в этом случае показывает последнее известное число, помечает его источник и называет причину, по которой живого нет.

### Три вкладки

Панель разделена по вопросам, а не по источникам данных:

| Вкладка | Вопрос | Что внутри |
|---------|--------|------------|
| **Аналитика** | что происходит на рынке | цена и уровни плана, детекторы, стакан, лента, новости, разбор работы робота |
| **Торговля** | что с деньгами | реальные сделки, путь к сделке, экономика круга, подключение биржи, события |
| **Тест** | чему верить в расчётах | виртуальная торговля, проверка допущений, журнал виртуальных сделок |

### «Что если»: допущения проверяются, а не только показываются

Вкладка «Тест» показывает, чем допущения оказались на живом потоке. Этого мало: главный вопрос — **что будет, если они окажутся другими**. Карточка «Что если» принимает цель, стоп, долю успеха, спред, долю тайм-стопов и размер позиции и отвечает тем же гейтом издержек, который решает судьбу настоящей сделки.

Считает Python, а не браузер (`GET /api/whatif` → `cost_gate.check`). Копия формулы на JavaScript разошлась бы с оригиналом на первой же правке ставок — и разошлась бы молча, показывая «окупается» там, где робот отказывает. Правило «числа считает Python, интерфейс их только показывает» здесь то же, что у аналитика ([[34-Analyst]]).

Кнопка «Как измерено» подставляет то, что дала виртуальная торговля: измеренную долю успеха и измеренную долю тайм-стопов. Это и есть проверка допущения — заложенные 50% против измеренных 14%, и сразу видно, что при измеренных числах гейт отказывает.

Право панели при этом не меняется: `/api/whatif` ничего не пишет, ничего не спрашивает у биржи и роботу ничего не передаёт. Вход — числа из формы, выход — ответ гейта.

Деление проведено по цене ошибки. Смешивать настоящие сделки с виртуальными в одной ленте нельзя: они выглядят одинаково, а стоят разного — и на телефоне, где видно один экран, перепутать их проще всего. Кошелёк и строка состояния остаются над вкладками: они отвечают на вопрос «всё ли в порядке вообще» и нужны в любой из трёх.

### Технические решения

- **Инкрементальное чтение.** Файлы сборщика — дописываемый gzip; к концу суток это десятки мегабайт. Декомпрессор и смещение сохраняются между опросами, дочитывается только новый хвост.
- **Только петлевой интерфейс.** Слушает `127.0.0.1`. С удалённого хоста — через SSH-туннель, а не открытым портом: панель отдаёт всю торговую картину, и публиковать её в сеть нельзя.
- **Без внешних зависимостей.** Стандартная библиотека и inline-разметка; ни одного запроса к CDN — это и офлайн-работа, и минимальная поверхность атаки ([[10-Security]], 10.6).
- **Панель не падает вместе с данными.** Ошибка обновления логируется, страница продолжает показывать последнее корректное состояние с отметкой возраста.

```bash
python ops/dashboard.py --port 8090
# удалённо:  ssh -L 8090:127.0.0.1:8090 user@host
```

## 13.7 Ротация и хранение

| Файл | Ротация | Хранение |
|------|---------|----------|
| `events.jsonl` | ежедневно + при 50 МБ, сжатие | 90 дней локально, 2 года в архиве |
| `state.db` (SQLite) | не ротируется; суточный снимок | 30 снимков + бессрочный архив |
| `trades.parquet` | ежемесячно | бессрочно |
| `exec.csv` | ежедневно | 180 дней |
| `heartbeat.json` | перезапись | — |

Логи пишутся через `logrotate` или средствами контейнера. Бэкап — ежедневно на внешнее хранилище: логи, лежащие только на упавшей машине, не помогли ещё никому.

## 13.8 Конвейер в research

```
data/state.db, data/exec.csv, data/events.jsonl
     │  ops/collect.py (ежедневно, по ssh/rsync)
     ▼
research/data/raw/
     │  research/etl.py  → валидация схемы, дедуп, типы, Decimal
     ▼
research/data/trades.parquet
     │  research/report.py
     ▼
research/reports/*.html   +   research/reports/*.json
```

ETL обязан **падать** при несовпадении схемы, а не молча пропускать строки. Тихая потеря 3% сделок сместит всю статистику, и вы об этом не узнаете.
