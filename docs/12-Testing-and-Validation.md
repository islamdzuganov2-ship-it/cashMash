# 🧪 12 · Тестирование и валидация

> Бэктест не доказывает, что стратегия работает. Бэктест доказывает, что стратегия работала бы, если бы вы знали заранее её параметры. Вся эта глава — про то, как отличить одно от другого.

## 12.1 Уровни тестирования

| Уровень | Что проверяет | Инструмент | Гейт |
|---------|--------------|-----------|------|
| L0 Юнит-тесты | корректность модулей | `pytest` | 100% зелёных, покрытие торгового пути > 90% |
| L1 Мок-биржа | обработка всех классов ошибок | локальный сервер с инжекцией | 0 необработанных веток, 0 дублей позиций |
| L2 Экономика | издержки смоделированы верно | сверка с live-выборкой | отклонение < 20% |
| L3 In-Sample | есть ли эдж в принципе | собственный бэктестер на тиках | см. 12.5 |
| L4 Out-of-Sample | эдж не выдуман | WFA + CPCV | см. 12.6 |
| L5 Робастность | эдж не на острие иглы | стресс, Монте-Карло, сенситивность | см. 12.7 |
| L6 Testnet | механика на живом потоке | `api-testnet.bybit.com`, 4 недели | 0 инцидентов, maker ratio > 80% |
| L7 Live $5 | реальные деньги, реальные ошибки | mainnet, минимальный размер, 4 недели | механика исправна |
| L8 Live $300+ | статистика | mainnet, сайзинг от риска | не хуже L6 −30% по expectancy в R |

Переход на следующий уровень **только** после прохождения предыдущего. Это не бюрократия: каждый уровень отсекает свой класс самообмана.

## 12.2 Качество данных — предусловие всего остального

| Требование | Почему |
|-----------|--------|
| **Тиковые сделки** (`publicTrade`), не свечи | Стратегия с целями 25 bps и стопами 15–100 bps на минутных свечах не тестируется: внутри свечи могло произойти что угодно |
| **Стакан L2** — если стратегия входит post-only | Без книги невозможно честно ответить, исполнилась бы ваша лимитная заявка. Это главный источник завышенных результатов maker-стратегий |
| Глубина ≥ 2 лет | Нужны разные режимы: бычий, медвежий, боковой, каскады ликвидаций |
| Та же биржа, что в live | Bybit, а не «крипта вообще»: спред, глубина и микроструктура различаются |
| Комиссия и фандинг в модели | По умолчанию их нет ни в одном фреймворке |
| Проверка целостности | Пропуски, дубликаты `execId`, немонотонные метки времени, выбросы цены |

### Модель исполнения post-only в бэктесте

Это то место, где бэктест врёт чаще всего.

```
Оптимистично (НЕЛЬЗЯ):  цена коснулась уровня → заявка исполнена
Консервативно (ТАК):    цена прошла уровень НАСКВОЗЬ на N тиков → исполнена
```

Разница принципиальна: при касании вы часто остаётесь неисполненным именно в тех случаях, где исполнение было бы прибыльным — цена отскочила, не дойдя до вас. Оптимистичное допущение превращает убыточную стратегию в прибыльную на бумаге.

Если доступна история стакана — моделируется очередь: считаем себя **последними** в очереди на своём уровне, исполнение только после того, как весь стоявший перед нами объём выбран.

**Скрипт проверки данных** (`research/check_data.py`) выполняется до любого бэктеста и выдаёт: покрытие по дням, гистограмму межсделочных интервалов, долю пропусков, выбросы > 10σ, список подозрительных окон, распределение спреда по часам UTC.

## 12.3 Бюджет параметров — сколько степеней свободы можно себе позволить

Ключевая величина — **минимальная длина бэктеста** (Bailey, Borwein, López de Prado, Zhu). Интуиция: чем больше конфигураций вы перебрали, тем выше максимум IS-Sharpe чисто случайно.

Ожидаемый максимум Sharpe среди `N` независимых бессмысленных стратегий растёт примерно как:

```
E[max SR] ≈ σ_SR × ( (1−γ)·Z⁻¹(1 − 1/N) + γ·Z⁻¹(1 − 1/(N·e)) )
```

Практический вывод без вывода формул: **если вы перебрали 10 000 комбинаций параметров на 2 годах данных, лучший результат почти наверняка будет выглядеть отлично и не будет значить ничего.**

Рабочие правила проекта:

| Правило | Значение |
|---------|----------|
| Число **одновременно** оптимизируемых параметров | ≤ 4 |
| Общее число оптимизируемых параметров по всему проекту | ≤ 8 |
| Число прогонов оптимизации регистрируется честно | журнал `research/trials.csv`, каждая попытка |
| Требуемое число OOS-сделок | ≥ 300 |
| Требуемый t-stat OOS | ≥ 2.0 (лучше 2.5 при большом числе trials) |
| Шаг сетки параметров | грубый; тонкая сетка = поиск шума |

Параметры делятся на три класса:

- **Структурные** (задаются один раз, не оптимизируются): таймфрейм, символ, сессии, режим ММ.
- **Физические** (берутся из спецификаций биржи, не подбираются): `minNotionalValue`, `qtyStep`, `tickSize`, ставки комиссии, потолок спреда.
- **Оптимизируемые** (≤ 4 одновременно): например `ATR_mult_SL`, `RR`, `EntryThreshold`, `T_hold_percentile`.

## 12.4 Кастомный критерий оптимизации

Оптимизация по «итоговой прибыли» или «profit factor» выбирает самые переобученные конфигурации: они максимизируют экстремум, а не устойчивость. Нужен собственный критерий.

```python
def objective(trades: list[Trade]) -> float:
    n = len(trades)
    if n < MIN_TRADES:              # отсечка малых выборок
        return 0.0

    r = np.array([t.net_r for t in trades])      # результат в R
    if r.sum() <= 0:
        return 0.0

    t_stat = r.mean() / (r.std(ddof=1) / np.sqrt(n))
    pf     = gross_profit(r) / max(gross_loss(r), 1e-9)
    dd     = max_relative_drawdown(r)            # доля, не проценты

    if dd > MAX_DD or max_consecutive_losses(r) > 8:
        return 0.0

    return t_stat * min(pf, 3.0) / 3.0 / max(dd, 0.01) ** 0.5
```

Три решения в этой формуле:

- **основа — t-статистика, а не прибыль**: она уже нормирована на разброс и на число сделок;
- **потолок на PF (3.0)**: PF = 40 на 12 сделках — это не отличная стратегия, это отсутствие выборки;
- **штраф за просадку** через корень: сильнее наказывает большие просадки, но не превращает критерий в «минимизируй DD любой ценой».

Метрики считаются **по сделкам**, а не по барам эквити: барная сетка сглаживает и систематически завышает Sharpe.

## 12.5 In-Sample: что считается «эдж есть»

| Метрика | Порог |
|---------|-------|
| Число сделок | ≥ 500 |
| Profit factor | ≥ 1.25 (для скальпинга с высоким winrate — ≥ 1.15 при N ≥ 2000) |
| t-stat средней сделки | ≥ 3.0 на IS |
| Expectancy после издержек | > 0 при **удвоенных** издержках |
| Max relative equity DD | ≤ 15% |
| Максимальная серия убытков | ≤ 8 |
| Доля прибыли от топ-5 сделок | ≤ 30% (иначе результат сделан выбросами) |
| Эквити по месяцам | ≥ 60% месяцев прибыльны |

## 12.6 Out-of-Sample: два независимых метода

### A. Walk-Forward Analysis

```
|--- IS 6 мес ---|- OOS 2 мес -|
        |--- IS 6 мес ---|- OOS 2 мес -|
                |--- IS 6 мес ---|- OOS 2 мес -|
                        ...
```

- Окно скользящее (rolling), не якорное — рынок нестационарен, старые данные вредят.
- На каждом IS-окне: оптимизация по кастомному критерию, берётся **одна** конфигурация.
- Склеенная OOS-кривая — это единственный результат, который можно кому-то показывать.

**Walk-Forward Efficiency:**
```
WFE = (средняя доходность OOS за период) / (средняя доходность IS за период)
```
| WFE | Интерпретация |
|-----|--------------|
| > 0.7 | хорошо, параметры устойчивы |
| 0.5–0.7 | приемлемо |
| 0.3–0.5 | подозрительно, вероятна подгонка |
| < 0.3 | подгонка, стратегия отклоняется |

Дополнительно: **доля прибыльных OOS-окон ≥ 60%**. Одно огромное окно, вытянувшее всю кривую, — это не устойчивость.

### B. Combinatorial Purged Cross-Validation (CPCV)

WFA даёт **одну** OOS-траекторию. CPCV даёт их распределение.

```
1. Разбить историю на N блоков (N = 12)
2. Выбирать все сочетания k блоков (k = 2) как тест → C(12,2) = 66 комбинаций
3. Между train и test — PURGE (удалить сделки, пересекающиеся по времени)
   и EMBARGO (буфер после теста, чтобы автокорреляция не протекала)
4. Для каждой комбинации: обучение → тест → метрика
5. Получаем распределение из 66 OOS-Sharpe
```

Смотрим не на среднее, а на:
- **медиану** (должна быть > 0);
- **долю комбинаций с положительным результатом** (≥ 65%);
- **5-й перцентиль** — это ваш реалистичный плохой сценарий.

### C. Probability of Backtest Overfitting (PBO)

Через CSCV: доля случаев, когда конфигурация, лучшая на IS-половине, оказывается **ниже медианы** на OOS-половине.

| PBO | Вердикт |
|-----|---------|
| < 0.3 | приемлемо |
| 0.3–0.5 | тревожно |
| **> 0.5** | стратегия — результат перебора, **отклоняется** |

### D. Deflated Sharpe Ratio

Поправка наблюдённого Sharpe на число испытаний, асимметрию и эксцесс распределения доходностей. Требование: **DSR даёт p < 0.05** при честно указанном числе trials из `research/trials.csv`.

Именно поэтому журнал попыток ведётся с первой оптимизации: занизив `N`, вы обманете только себя, и узнаете об этом на реальном счёте.

## 12.7 Робастность

| Тест | Как | Критерий прохождения |
|------|-----|---------------------|
| **Сенситивность параметров** | перебор ±30% вокруг выбранной точки, шаг 10% | результат положителен на ≥ 70% соседних точек; выбранная точка — **не** глобальный пик, а центр плато |
| **Стресс издержек** | спред ×2, комиссия ×2, слиппедж ×3 | expectancy > 0 |
| **Стресс латентности** | задержка входа 100/250/500 мс | деградация < 40% при 250 мс |
| **Монте-Карло: перестановка сделок** | 10 000 перестановок порядка | 95-й перцентиль макс. просадки ≤ лимита счёта |
| **Монте-Карло: бутстрап** | ресэмплинг сделок с возвратом | доля траекторий с итоговым убытком < 5% |
| **Монте-Карло: рандомизация исполнения** | случайное проскальзывание из эмпирического распределения | медианный результат положителен |
| **Удаление лучших сделок** | убрать топ-5% сделок | остаётся прибыльной |
| **Сдвиг данных** | старт теста сдвинут на 1–20 дней | разброс результата < 30% |
| **Кросс-инструмент** | те же параметры на коррелированном символе | не обязана работать, но катастрофа = тревожный знак |
| **Разбивка по годам/кварталам** | — | нет года с провалом > 2× типичной просадки |

## 12.8 Testnet и live-микро (L6–L7)

4 недели на testnet, затем 4 недели на mainnet с депозитом $5.

Сравниваем с бэктестом **на том же периоде** (гоняем бэктест поверх тех же дат после окончания):

| Метрика | Допустимое расхождение |
|---------|----------------------|
| Число сделок | ±15% |
| Winrate | ±7 п.п. |
| Средняя сделка в bps | ±25% |
| **Maker ratio** | факт ≥ 80%; расхождение с моделью > 15 п.п. — дефект |
| Фактическая комиссия в bps | ±10% от модели |
| Проскальзывание taker-выходов | факт не хуже модели на 1 bps |
| Уплаченный фандинг | ≈ 0; заметная величина = сломана тайм-логика |
| Максимальная просадка | факт ≤ модель × 1.5 |

Расхождение сверх допустимого — это **дефект модели, а не «рынок изменился»**. Возврат к [[04-Microstructure-and-Costs]] и уточнение издержек.

> **Ограничение уровня L7.** На депозите $5 сравнение по прибыльности статистически бессодержательно: размер позиции фиксирован, сайзинга нет. L7 проверяет **механику** — что ордера проходят, ошибки обрабатываются, фандинг списывается, реконнекты не ломают учёт. Вывод «стратегия прибыльна» на этом уровне делать нельзя; он делается на L4 (историческая валидация) и подтверждается на L8. См. [[22-Micro-Capital]].

## 12.9 Чего категорически не делаем

```
✗ Оптимизировать на всей истории и показывать её как результат
✗ Смотреть на OOS, ухудшать параметры, снова смотреть на OOS
  (это превращает OOS в IS — и у вас больше нет честной выборки)
✗ Выбирать лучшую из 50 стратегий и считать её Sharpe как есть
✗ Останавливать тест на «хорошей» дате
✗ Убирать «аномальные» убыточные периоды как «нерепрезентативные»
✗ Тестировать на фиксированном спреде
✗ Тестировать на синтетических тиках
✗ Игнорировать комиссию, фандинг и стоимость неисполнения post-only
✗ Считать Sharpe по барам эквити вместо сделок (завышает)
✗ Запускать live «пока идёт тестирование, чтобы не терять время»
```
